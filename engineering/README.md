# 让 Agent 在 REAPER 里精确落点

> 你的 Agent 能写出**正确**的音符，但写不在**正确**的位置上。
>
> 这不是模型不够聪明。
> **是你的接口在说「秒」，而它在想「小节」。**

---

## 一、症状

你给 Agent 一个任务：

> 「在第 5 小节第 1 拍写一个 C4，时值一拍。」

它写完了。你播一下。

**音符在那儿，但不完全在那儿。**

- 有时候偏了整整一个**小节**
- 有时候只偏几十毫秒，你会说"差不多"
- 有时候它自己也不确定，在 5.1 和 5.2 之间反复横跳

你调 prompt、换模型、加 few-shot —— 好一点，但**永远到不了"精确"**。

你开始怀疑：是不是模型就是干不了这个？

---

## 二、不是模型笨

一句话说清：

> **生成模型在 `1+1=2` 这类形式推理上是可靠的。
> 它的失效恰恰说明 —— 输入表示本身缺乏可计算的精确性。**

模型不是算不出来。**是你没给它算得出来的东西。**

试想一下：如果它的任务是「把 A 数组的第 3 个元素改成 5」，它能做到位。
但如果任务是「把第 5 小节第 1 拍换算成秒」—— 它需要知道：

- 这个工程的拍号是什么？
- 中途换过拍号吗？
- 换的时候，`一拍`的物理长度变了吗？
- 变了几次？

**这些信息不在你的接口里。** 模型只能猜。

---

## 三、病因：接口形状不对

看一个典型的 DAW MCP server 的接口（真实存在）：

```lua
-- 写音符的接口
notes.add({ start_position = 12.48, end_position = 13.02, pitch = 60 })
--                        ↑ 秒                      ↑ 秒
```

**整个接口里没有任何一处接受「小节」或「拍」。**

于是 Agent 必须自己做这件事：

```
「第 5 小节第 1 拍」  ──[ ??? ]──▶  12.48 秒
                      ↑
              这一步它只能心算
```

**而这个换算需要时间签名映射表 —— 模型手里没有。**

### 正确的接口应该长这样

```lua
notes.add({ bar = 5, beat = 1, pitch = 60, length_beats = 1 })
```

**模型说它想说的，转换由机器做。**

---

## 四、正确的换算是什么

核心只有一条：**「一拍」的长度由拍号决定，而拍号会变。**

### 4.1 通行的写法（错的）

```
AbsTick = ((M − 1) · BPI + (T − 1)) · TPB         TPB = PPQ × 4 / Denom
```

`M` = 小节号，`T` = 拍号（均自 1 起计）。

**它假设全程只有一把尺子。** 一旦中途换拍号，就崩了。

### 4.2 反例

设工程为：

| 段 | 小节 | 拍号 | BPI | Denom | 每小节 tick |
|---|---|---|---|---|---|
| 1 | 1–4 | 4/4 | 4 | 4 | **3840** |
| 2 | 5–10 | 3/4 | 3 | 4 | **2880** |
| 3 | 11–18 | 6/8 | 6 | 8 | **2880** |

PPQ = 960。问：第 5 小节第 1 拍（`5.1.00`）的绝对 tick？

```
上面的式子（拿段 2 的 BPI 从第 1 小节硬乘）：
    ((5 − 1) × 3 + 0) × 960 = 11520     ❌

真实值（分段累加）：
    4 小节 × 3840 = 15360                ✅

误差 = 3840 = 整整一个 4/4 小节
```

**这就是「切了拍号之后音符系统性偏移」的根因。**

> 换句话说：原式以为函数是**一条直线**，实际是**一条折线**。
> 对直线，一个乘法通吃；对折线，只能**分段求和**。

### 4.3 通式

```
abs_tick(B, T) = Σ_{s < k} [ (eb_s − sb_s + 1) · BPI_s · TPB_s ]
               + ( (B − sb_k) · BPI_k + (T − 1) ) · TPB_k
```

其中 `k` 是包含小节 `B` 的段。

**关键改动只有一处：**

> **「减一」没变，但它从「全局减一」降级成了「段内减一」。**

### 4.4 退化性质

`n = 1` 时（全曲单一拍号），通式**精确退化为原式**。

也就是说：**替换实现不会改变单拍号工程的任何行为**，可以安全部署。

### 4.5 一个常被忽略的点：反向映射

```
正向  bar.beat → tick   ：一个公式，手算也行
反向  tick → bar.beat   ：必须依赖各段累计边界 S_s
```

`bar.beat ↔ tick` 是**分片线性、严格单调的双射**，所以反向有唯一解 ——
**但反向的落脚点是那串累计边界 `S_s`，不是公式。**

**正向可手算，反向不可。** 这是这个概念里唯一"不知道就会做错"的地方。

## 五、证据：这不是纸上推导

上面那个 3840 tick 的反例，和通式本身，**都在真实 DAW 上实测过**。

### 5.1 实测方法

在一个 `4/4 (1–4) → 3/4 (5–10) → 6/8 (11–18)` 的测试工程里，
对**每一小节的每一拍**，同时用三条独立路径求位置：

| 路径 | 来源 |
|---|---|
| **A** | 本文的通式（纯算术） |
| **B** | REAPER `TimeMap_GetMeasureInfo()`（查表） |
| **C** | REAPER `TimeMap2_beatsToTime()` → `TimeMap2_timeToQN()`（换算） |

**三条路径互相独立。全一致才算验证。**

### 5.2 实测结果

```
REAPER 版本 : 7.73/x64
测试 PPQ    : 960
对照总数    : 82     一致 : 82     不一致 : 0
```

抽样：

| 小节 | 拍 | 通式 (QN) | REAPER-Info | REAPER-B2T | |
|---|---|---|---|---|---|
| 1 | 1 | 0.000000 | 0.000000 | 0.000000 | ✅ |
| 5 | 1 | 16.000000 | 16.000000 | 16.000000 | ✅ |
| 11 | 1 | 34.000000 | 34.000000 | 34.000000 | ✅ |
| 18 | 6 | 57.500000 | 57.500000 | 57.500000 | ✅ |

反例复现：

| 位置 | 通式 (tick) | 原式 (tick) | 误差 |
|---|---|---|---|
| `5.1.00` | 15360 | 11520 | **3840** ✅ |
| `9.2.00` | 27840 | 24000 | **3840** ✅ |
| `11.1.00` | 32640 | 28800 | **3840** ✅ |

### 5.3 怎么自己跑

```
REAPER → Actions → Show action list
       → New action → Load ReaScript
       → 选中 code/matcs_verify_reaper.lua  → 运行
```

脚本会：

1. 备份你当前的 tempo map
2. 自建标准测试工程（`4/4 → 3/4 → 6/8`）
3. 探测 API 的索引约定（不猜，实测）
4. 逐小节逐拍做三方对照
5. 复现上面那个 3840 tick 反例
6. **自动还原**你的 tempo map（全程包在 Undo 里）

结果输出到 REAPER 控制台，同时写入 `REAPER资源目录/MATCS-verify-result.txt`。

> ⚠️ **第一次请在空工程里跑。**
> 💡 想拿真实工程验证？把脚本开头的 `USE_CURRENT_MAP` 改成 `true`，它就完全不写任何东西。

## 六、修法：给 MCP server 加一个 bar:beat 接口

不用重写，**加一层**。

### 6.1 写入路径

```lua
-- 之前：Agent 必须自己把「第 5 小节第 1 拍」算成 12.48 秒
-- notes.add({ start_position = 12.48, pitch = 60 })

-- 之后：Agent 说它想说的
-- notes.add({ bar = 5, beat = 1, pitch = 60, length_qn = 1 })
```

核心实现（**完整可运行版见 [`code/matcs_agent_helpers.lua`](code/matcs_agent_helpers.lua)**）：

```lua
-- 位置：(小节, 拍) → 绝对 QN
local function bar_beat_to_qn(bar, beat)
    local _, qn_start, _, _, tdenom = reaper.TimeMap_GetMeasureInfo(0, bar - 1)
    return qn_start + (beat - 1) * (4 / tdenom)   -- 每「拍」= 4/分母 个 QN
end

-- 在音乐坐标处写一个音符
local function add_note_at(take, bar, beat, pitch, length_qn)
    local qn = bar_beat_to_qn(bar, beat)

    local t0 = reaper.TimeMap2_QNToTime(0, qn)
    local t1 = reaper.TimeMap2_QNToTime(0, qn + length_qn)

    return reaper.MIDI_InsertNote(take, false, false,
        reaper.MIDI_GetPPQPosFromProjTime(take, t0),
        reaper.MIDI_GetPPQPosFromProjTime(take, t1),
        0, pitch, 96, true)
end
```

### ⚠️ 时值别用「拍」，用 QN

这一处最容易踩：

```
拍号 4/4 时，「一拍」= 1 个四分音符
拍号 6/8 时，「一拍」= 1 个八分音符      ← 变了
```

**如果时值跨过变拍号点，说「两拍」就是有歧义的** ——
是起始小节的两拍，还是终点小节的两拍？

**用 QN 表达则没有这个问题**（QN 不随拍号变化），所以上面的接口收 `length_qn`。

> 如果你确实要用「拍」，`code/matcs_agent_helpers.lua` 里也提供了
> `add_note_at_beats()`，它**明确采用「起始小节的拍长」**作为解释策略。
> 策略是显式的，但跨变拍号点时仍会和直觉打架 —— 所以我们默认不用它。

### 6.2 读取路径（同样重要）

只改写入没用 —— Agent 写得进去，但**读不出来自己写在哪**。

```lua
-- 把 PPQ 转回「小节.拍」
local function ppq_to_bar_beat(take, ppq)
    local t = reaper.MIDI_GetProjTimeFromPPQPos(take, ppq)
    local beats_in_bar, measure, cml, fullbeats, cdenom =
        reaper.TimeMap2_timeToBeats(0, t)
    --  beats_in_bar : 小节内第几拍（0-based）
    --  measure      : 小节号（0-based）
    --  cml          : 当前每小节拍数（= 拍号分子）
    --  cdenom       : 当前拍号分母
    return measure + 1, math.floor(beats_in_bar) + 1
end
```

**改完之后，Agent 的完整闭环才成立：**

```
说「第5小节第1拍」→ 写进去 → 读回来 → 还是「第5小节第1拍」
```

## 七、这条路的边界

**别把这套东西当万能药。** 以下几条是硬边界：

| 边界 | 说明 |
|---|---|
| **段表必须外部提供** | 本方法**不从音频推断拍号**。那是 MIR 的概率估计问题 |
| **不校验前提** | 你传什么它算什么。段表错了，结果就错 |
| **密集变拍号时失效** | 当拍号"每小节一变"，公式的杠杆归零 —— 此时正解不是更好的公式，而是**拍号事件表 + 二分查找** |
| **取整误差无严格上界** | 变拍号情形下只有实测观测，没有证明 |
| **仅一种宿主软件验证过** | 目前只有 REAPER 7.73。其他 DAW 未验 |

**一句话：本方法是计算器，不是审计员。**
